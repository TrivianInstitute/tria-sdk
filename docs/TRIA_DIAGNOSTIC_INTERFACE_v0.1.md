# TRIA Diagnostic Interface v0.1

**Status:** implemented machine-facing contract  
**Implementation status:** implemented in `tria-sdk` `0.1.0a5`  
**Compatibility target:** TRIA SDK `0.1.0a5`, operational specification `0.1.2`  
**Canonical operation name:** `tria.diagnose`

## 1. Purpose

`tria.diagnose` is a read-only, inspectable diagnostic interface for asking a bounded question about an existing TRIA relationship and a proposed consequential action:

> What governance-relevant conditions, unresolved uncertainties, or relational signals may be absent from the caller's current representation?

The diagnostic interface does not create authority. It does not grant permission, infer legitimate real-world consent, authenticate actors, execute actions, modify relational state, or convert an advisory interpretation into a governance rule.

Its purpose is to expose relevant state and missing checks before a caller decides what to do next.

## 2. Design principles

The interface MUST preserve the existing TRIA architectural and epistemic boundaries:

1. **Enforcement and diagnosis remain distinct.** Existing `GovernanceDecision` outcomes remain authoritative for encoded governance checks. Diagnostic signals cannot weaken or override them.
2. **Hard outcomes come from current governance state.** `BLOCK`, `REQUIRE_CONSENT`, `PAUSE`, `DEFER`, and `ESCALATE` are reported as governance findings only when produced by an applicable TRIA governance evaluation.
3. **Advisory signals remain advisory.** Differentiation, convergence, optionality, or other interpretive signals do not automatically acquire governance authority.
4. **Unknown remains unknown.** Missing host authentication, absent external evidence, unresolved provenance, or unavailable context MUST be surfaced as unknown rather than guessed.
5. **Observation is not interpretation.** Existing epistemic distinctions among `OBSERVATION`, `INFERENCE`, `INTERPRETATION`, and `SHARED_CLAIM` MUST be preserved.
6. **Disagreement is not erased.** Contested or divergent claims remain separately attributable.
7. **No false precision.** v0.1 does not require numeric confidence values. A detector MAY expose a numeric confidence only when the detector, calibration method, and provenance are explicitly identified.
8. **Read-only by default.** Diagnosis MUST NOT itself append governance events, mutate permissions, grant consent, change lifecycle state, execute transport, or trigger external side effects.
9. **Current state, not stale authorization.** A diagnostic report is a snapshot and MUST NOT be treated as an execution authorization token. Consequential execution remains subject to final re-authorization at the existing execution boundary.
10. **Falsifiability.** Every nontrivial finding SHOULD expose the evidence or rule that produced it so a caller can inspect, contest, or reproduce the result.

## 3. Developer operation

The implemented developer-facing shape is:

```python
from tria import AttributableObservation, diagnose

report = diagnose(
    relationship,
    request,
    observations=(
        AttributableObservation("host_authentication", True, ("host:auth:1",)),
        AttributableObservation("external_authority_current", True, ("host:intent:1",)),
        AttributableObservation("reversibility", True, ("host:recovery:1",)),
    ),
)
```

The primary v0.1 request reuses `InvocationRequest` rather than inventing a parallel action model. That keeps diagnostics aligned with the same declared actor, action, target, context resources, capability requirements, consent requirements, purpose, and conditions used by `Runtime.evaluate`.

The current implementation exports `AttributableObservation`, `DiagnosticReport`, and `diagnose` from the top-level `tria` package. `DiagnosticReport.to_dict()` returns the schema-shaped wire representation.

## 4. Inputs

### 4.1 Required inputs

A diagnostic evaluation requires:

- an existing TRIA `Relationship` or compatible relationship object exposing `relationship_id` and current `state`;
- a proposed `InvocationRequest`;
- an evaluation timestamp generated by the implementation.

### 4.2 Optional inputs

The host MAY provide additional attributable observations. The initial implementation recognizes:

- `host_authentication`;
- `external_authority_current`;
- `reversibility`.

Each is supplied as an `AttributableObservation` with a nonempty `observation_type`, a value, and one or more `source_refs`.

Future versions MAY add differentiation measurements, external risk observations, dependency or downstream-effect descriptions, or named detector outputs. Optional observations MUST identify their source and evidence class. Unattributed free-form assertions MUST NOT be silently promoted to fact.

### 4.3 Inputs TRIA must not invent

The diagnostic interface MUST NOT infer without evidence:

- the real-world identity behind an actor label;
- whether legal consent exists;
- whether a human understood a disclosure;
- whether an external resource is truthful or complete;
- whether a model is conscious, sentient, deceptive, aligned, or safe;
- the downstream physical effects of an action not represented by the host;
- calibrated probabilities from uncalibrated heuristics.

These conditions belong in `unknowns` or attributable advisory findings when evidence exists.

## 5. Output model

A v0.1 diagnostic report has six top-level semantic sections:

1. `summary`
2. `governance_findings`
3. `diagnostic_signals`
4. `unknowns`
5. `suggested_checks`
6. `provenance`

The canonical JSON Schema is `schemas/tria-diagnostic-report.v0.1.schema.json`.

## 6. Summary

`summary` gives the caller a compact machine-readable disposition without pretending to replace runtime authorization.

Values are:

- `clear`: no applicable hard governance failure was found and no advisory condition or material unknown currently requests review;
- `review`: no hard governance failure was found, but one or more advisory signals or material unknowns warrant inspection;
- `blocked`: at least one applicable governance evaluation returned `BLOCK`;
- `consent_required`: at least one applicable governance evaluation returned `REQUIRE_CONSENT`;
- `paused`: applicable runtime/lifecycle governance returned `PAUSE`;
- `deferred`: applicable governance returned `DEFER`;
- `escalation_required`: applicable governance returned `ESCALATE`.

The implementation preserves every individual governance finding and applies summary precedence in this order: `BLOCK`, `REQUIRE_CONSENT`, `PAUSE`, `ESCALATE`, `DEFER`, then advisory review/clear.

`summary` is descriptive. It is not an authorization token.

## 7. Governance findings

`governance_findings` contain deterministic or policy-derived results from existing TRIA governance evaluation.

Each finding includes:

- `outcome`: one of the existing `GovernanceOutcome` values;
- `policy_id`;
- `policy_version`;
- `reason`;
- `evaluated_at`;
- `evidence_class`: `enforced`;
- `evidence_refs`.

The implementation reuses `Runtime.evaluate` rather than reproducing governance logic independently.

Examples include:

- invalid relationship history;
- requester not registered as a participant;
- missing, expired, purpose-mismatched, or condition-unsatisfied consent;
- missing, expired, purpose-mismatched, or condition-unsatisfied capability permission;
- ambiguous permission race;
- invalid lifecycle capability;
- paused or blocked runtime lifecycle.

Other governance families remain available through their existing direct interfaces and MAY be incorporated into later diagnostic versions where the request model explicitly represents them.

## 8. Diagnostic signals

`diagnostic_signals` surface relevant but non-authoritative conditions that may warrant inspection.

Each signal includes:

- `signal_type`;
- `evidence_class`: `derived` or `advisory`;
- `reason`;
- `source_refs`;
- `governance_effect`: `none` in v0.1.

### 8.1 Epistemic integrity

The initial implementation can surface:

- `contested_claim_in_context` when a referenced TRIA claim is `CONTESTED`;
- `missing_provenance` when a referenced claim has neither `source_refs` nor `derived_from` provenance.

The implementation inspects actual claim type/status rather than inferring epistemic quality from prose alone.

Future versions may add `interpretation_used_as_observation`, `superseded_or_withdrawn_claim_in_context`, and additional disagreement diagnostics as the underlying state model exposes sufficient evidence.

### 8.2 Differentiation and convergence

TRIA already exposes attributable differentiation observations through `differentiation.py`, but v0.1 `diagnose` does not yet automatically translate those measurements into diagnostic signals. When added, any such signals remain advisory unless separately mapped into governance by an adopted policy.

Potential future signals include:

- `crystallization_risk`
- `fragmentation_risk`
- `collapse_or_stagnation_risk`
- `generative_coherence`

### 8.3 Recoverability and optionality

The initial implementation accepts an attributable `reversibility` observation. When its value is explicitly `False`, the report may surface `irreversible_action` as advisory evidence.

TRIA does not infer reversibility from an action string alone. If no attributable reversibility evidence is supplied, the report surfaces `reversibility_unverified` as an unknown.

Future versions may add evidence-backed signals such as:

- `recovery_path_absent`
- `option_set_reduction`
- `independent_agent_elimination`

### 8.4 Authority freshness beyond encoded state

TRIA can evaluate encoded authority according to its own event history. It does not claim that the real-world principal still endorses that authority unless the host supplies attributable evidence.

The initial implementation therefore uses:

- `external_authority_freshness_unverified` when no host evidence is supplied;
- `external_authority_stale_or_unconfirmed` as an advisory signal when attributable host evidence does not confirm current authority.

This distinction prevents encoded authorization from being misrepresented as proof of current real-world intent.

## 9. Unknowns

`unknowns` are first-class outputs, not failures of the interface.

Each unknown contains:

- `unknown_type`;
- `reason`;
- optional `required_source`;
- optional `required_check`;
- `materiality`: `informational`, `review`, or `execution_relevant`.

The initial implementation may surface:

- `host_authentication_unverified`;
- `external_authority_freshness_unverified`;
- `reversibility_unverified`.

An `execution_relevant` unknown does not automatically become a TRIA `BLOCK` unless an adopted governance rule makes that unknown disqualifying.

## 10. Suggested checks

`suggested_checks` are non-binding next inspections intended to reduce uncertainty or repair a detected condition.

Examples include:

- authenticate the requesting actor in the host;
- revalidate current principal intent;
- inspect a contested claim and preserve disagreement;
- supply provenance for a context claim;
- document or simulate a recovery path;
- inspect alternatives before an irreversible action.

Suggested checks MUST NOT be presented as actions already taken.

## 11. Evidence classes

v0.1 defines four evidence classes:

### `enforced`

A result directly produced by applicable TRIA governance logic or an adopted policy with governance authority.

### `derived`

A deterministic transformation of attributable observations or state using a named transparent method, where the result itself has no governance authority unless separately adopted.

### `advisory`

An attributable interpretation, heuristic, or diagnostic prompt that may be useful but does not establish a fact or governance outcome.

### `unknown`

A material variable for which sufficient evidence is absent or outside TRIA's trusted boundary.

A report MUST NOT relabel an `advisory` or `unknown` result as `enforced` merely because the caller prefers a stronger answer.

## 12. Numeric confidence

Numeric confidence is OPTIONAL and absent from the initial v0.1 implementation.

If a future detector emits `confidence`, the finding MUST also identify:

- `detector_id`;
- `detector_version`;
- `calibration_method` or explicit `uncalibrated` status;
- `calibration_reference` when available.

Uncalibrated numeric scores MUST NOT be interpreted as probabilities.

## 13. Read-only behavior

The canonical `tria.diagnose` operation is pure with respect to relationship state in v0.1.

It MUST NOT:

- append events;
- record a governance decision event merely because diagnosis was requested;
- mutate consent or permission records;
- adopt policy;
- change lifecycle state;
- invoke a provider;
- resolve external resources through side-effecting callbacks;
- execute transport;
- grant or revoke authority.

A host MAY separately record that it requested or received a diagnostic report, but that is outside the pure diagnostic operation and requires its own governed write/disclosure semantics where applicable.

## 14. Relationship to Runtime and ExecutionBridge

The diagnostic interface complements but does not replace the existing execution path.

Recommended flow:

```text
proposed InvocationRequest
        |
        v
  tria.diagnose()        <- read-only inspection
        |
        +--> governance findings
        +--> advisory signals
        +--> unknowns
        +--> suggested checks
        |
        v
host decides whether to revise request / obtain evidence / continue
        |
        v
Runtime.prepare()
        |
        v
ExecutionBridge.execute() <- final re-authorization remains authoritative
```

A prior `clear` diagnostic report MUST NOT cause `ExecutionBridge` to skip final governance checks. This property is covered by `tests/test_diagnostic.py`.

## 16. What v0.1 explicitly does not establish

A diagnostic report does not establish:

- that an action is morally correct;
- that a deployment is safe;
- that a person legally consented;
- that a person understood a request;
- that an external identity is authentic;
- that a model is aligned, conscious, deceptive, or trustworthy;
- that an advisory signal predicts harm;
- that a numeric score is probabilistically calibrated;
- that a `clear` report means no relevant unknown exists outside the represented state.

The interface improves inspectability of represented relational state. It does not abolish the limits of representation.

## 17. Implementation acceptance criteria

`tria.diagnose` is marked implemented because executable tests currently demonstrate that:

1. it is read-only with respect to relationship history;
2. it reuses applicable `Runtime.evaluate` governance outcomes without weakening them;
3. `BLOCK` and `REQUIRE_CONSENT` remain distinguishable, while the existing runtime retains distinct `PAUSE` semantics;
4. advisory signals do not acquire governance authority;
5. contested claims are preserved and surfaced without semantic overwrite;
6. absent host identity evidence appears as unknown rather than authenticated fact;
7. absent reversibility evidence is not fabricated;
8. a prior diagnostic `clear` cannot bypass final `ExecutionBridge` re-authorization;
9. report output validates against the canonical diagnostic-report schema;
10. provenance identifies the SDK, operational spec, and diagnostic spec versions used.

Future extensions MUST preserve these properties or explicitly version the contract.

## 18. Future extensions

After v0.1 is further falsified, later versions may consider:

- named detector registries;
- calibrated detector confidence metadata;
- explicit comparison of alternative action paths;
- before/after diagnostic deltas;
- richer differentiation integration;
- MCP tool exposure;
- A2A skill exposure;
- Unknown-Unknown Challenge benchmark integration;
- adopted policies that deliberately map selected diagnostic signals into enforceable governance.

Those extensions must not silently collapse the distinction among measurement, interpretation, and authority.
